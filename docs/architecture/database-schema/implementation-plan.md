# Database Schema Redesign Implementation Plan

Replace the current Supabase migration chain and its application contracts with the accepted schema
in [`database-schema.dbml`](database-schema.dbml). The database is development-only and resettable,
so this is an atomic clean-baseline cutover: no data backfill, dual writes, compatibility views, or
legacy RPC wrappers.

## Outcome

The work is complete when a fresh `supabase db reset` produces only the accepted tables and the web
application passes every supported space, memory, asset, comment, reaction, and settings flow against
that database.

The redesign must preserve these product contracts:

- Memory visibility remains `timeline | vault` in the database and application.
- UI and route terminology may continue to use `photo`; `asset` is the persistence model.
- The private storage bucket may remain `memory-photos`; the schema stores provider-neutral object
  locators and does not expose bucket details to clients.
- Create/edit request idempotency is removed. Comment creation idempotency remains.
- Memory optimistic concurrency remains based on `memories.updated_at`.
- Authentication and tenant authority are always derived from the verified session.

## Delivery Strategy

Delete the existing files under `supabase/migrations/` and replace them with one self-contained
baseline migration. Do not add a destructive migration after the current chain: replaying obsolete
tables and functions before dropping them makes reset slower and leaves dead contracts in review.

The baseline and all affected application consumers form one atomic cutover. Intermediate commits may
be organized by the work units below, but only the completed branch is releasable.

## Target Database Contract

### Identity and tenancy

Implement `users`, `spaces`, and `space_members` exactly from the DBML, with these physical rules:

- `users.id` is an internal UUID generated by the application database.
- `users.auth_subject` stores `auth.users.id::text` and is the only link to the authentication
  provider. It is unique and non-blank.
- `syncCurrentUser` upserts by `auth_subject`; it must not set the internal `users.id` from the auth
  UUID.
- SQL helpers resolve the current internal user once from `auth.uid()::text` and use that UUID for all
  domain foreign keys.
- Active memberships enforce unique `user_id`, `(space_id, user_id)`, and `(space_id, role)` through
  partial unique indexes.
- Composite keys `(id, user_id, space_id)` and `(id, space_id)` remain available for tenant-safe
  foreign keys.
- An active space has one owner and at most one partner. Space creation and joining enforce the lower
  and upper bounds atomically; direct table writes remain unavailable to application roles.
- `invite_code_expires_at` is null exactly when `invite_code` is null.

### Generic rate limiting

Replace `join_attempt_limits` and `invite_regeneration_attempt_limits` with `rate_limits`:

- Use explicit scopes such as `space_join` and `invite_regeneration`.
- Use the authenticated subject as an opaque `subject_key`; hash any future sensitive subject before
  storage.
- Lock a row with `FOR UPDATE` before pruning and appending rolling-window timestamps.
- Bound `attempts` defensively and index `expires_at` for cleanup.
- Keep policy values such as limits and windows inside the owning RPCs; do not add configuration
  tables.

### Memories and attempts

Replace `memory_creation_attempts` and `memory_edit_attempts` with `memory_attempts`:

- Store normalized memory details on the attempt during preparation.
- A create attempt has no `memory_id` or `expected_updated_at` until completion.
- An edit attempt requires both `memory_id` and `expected_updated_at`.
- A completed attempt requires `memory_id` and `completed_at`.
- Allowed state transitions are enforced in SQL; callers cannot move completed, failed, conflicted,
  or expired attempts back into processing.
- Finalization locks the attempt and target memory before validating state or version.
- Create finalization inserts one memory and publishes selected staged assets atomically.
- Edit finalization checks `expected_updated_at`, publishes staged assets, retains selected existing
  assets, updates positions and cover ownership, and queues removed object locators for cleanup.
- Create/edit attempts contain no idempotency key or request fingerprint.

Use this application workflow:

1. Validate and normalize the complete form on the prepare endpoint.
2. Create one `memory_attempt` and its `memory_attempt_assets` selection.
3. Create staged `memory_assets` and their object rows for new uploads.
4. Return `attemptId` and original-object upload descriptors.
5. Upload originals directly to private storage.
6. Finalize by `attemptId`; validate bytes and create variants before the SQL publication transaction.
7. Return the published memory ID, visibility, and encoded `updated_at` version where applicable.

Preparation must run even when no new photos exist. This gives every mutation one attempt identity and
lets a finalization retry continue the same operation without restoring request idempotency.

### Assets and storage objects

Replace `memory_photos`, both photo staging tables, and their path columns with the asset model:

- `memory_assets` owns logical images and has exactly one owner: `memory_id` or
  `staging_attempt_id`.
- `memory_asset_objects` owns `original`, `cover`, and `detail` object variants and their processing
  state.
- `memory_attempt_assets` records the complete ordered selection, including retained assets and one
  optional cover.
- New attempts create all required object rows before browser upload so storage policies can authorize
  the exact paths.
- The original moves through `pending -> uploaded -> processing -> ready` after byte validation.
- Derived variants move through `pending -> processing -> ready` after successful storage upload.
- Set `failure_code` on failed objects and require `ready_at` exactly for `ready` objects.
- Finalization requires every selected asset's required objects to be ready.
- Published assets require a nonnegative position unique within the memory; staged assets have no
  published position.
- `memories.cover_asset_id` must reference an asset owned by the same memory.
- Storage policies resolve access through object, asset, space, active membership, and active user.
- Object paths remain opaque outside server/storage code. API responses expose only application URLs.

### Cleanup

Replace memory-specific cleanup tables and RPCs with `resource_cleanup`:

- Queue each abandoned or replaced object locator once by `(resource_kind, resource_locator)`.
- Claim bounded batches with `FOR UPDATE SKIP LOCKED` and a short `locked_until` lease.
- Treat a missing external object as successful cleanup.
- On failure, increment `attempt_count`, store a bounded failure code, and set `retry_after` with
  backoff.
- Mark success with `cleaned_at`; do not delete audit rows during request handling.
- Keep cleanup opportunistic for now by invoking one shared cleanup function from memory preparation
  routes. Do not add a worker or queue until request-driven cleanup is measurably insufficient.

### Engagement

Keep the current comment and reaction behavior while rebuilding their constraints and functions:

- Comments retain `(author_user_id, idempotency_key)` uniqueness and request fingerprints.
- Comment reads and mutations validate the complete memory-space-membership-user ownership chain.
- Comment edits increment `version`; deletes remain soft deletes with version checks.
- Reactions remain one current reaction per membership and memory.
- Reaction summaries retain counts, current-member reaction, and member display names.
- Memory deletion makes comments and reactions unavailable without leaking cross-space existence.

## Baseline Migration Construction

Create one migration such as `supabase/migrations/20260915000000_database_schema.sql` in this order:

1. Enable required extensions and create `private` schema.
2. Create enums: `space_member_role`, `memory_visibility`, `memory_attempt_type`,
   `memory_attempt_status`, `memory_asset_type`, `memory_asset_variant_type`, and
   `memory_asset_object_status`.
3. Create tables in dependency order: users, spaces, space members, rate limits, memories without the
   cover FK, attempts, assets, asset objects, attempt assets, comments, reactions, and cleanup.
4. Add cyclic and composite foreign keys after all participating tables exist.
5. Add check constraints, partial unique indexes, read-path indexes, and update triggers.
6. Create the private `memory-photos` bucket with the existing 5 MiB and MIME restrictions.
7. Create private identity, active-membership, authorization, rate-limit, storage-path, and cleanup
   helpers with `search_path = ''` and schema-qualified references.
8. Enable RLS on every exposed application table and define least-privilege policies.
9. Recreate public space, settings, memory, comment, and reaction RPCs using authenticated-session
   authority.
10. Revoke default function/table privileges, then grant only required `SELECT` and `EXECUTE`
    privileges to `authenticated`; reserve cleanup administration for `service_role`.

Every foreign-key source column used for joins or deletes needs a supporting index unless it is already
the leading column of a unique index. Read-path indexes must cover active membership lookup, timeline
and vault pagination, active comments, reaction summaries, attempt expiry/state, ready objects, and
pending cleanup claims.

## Application Work Units

### 1. Identity, spaces, and settings

Update:

- `apps/web-app/src/features/space-setup/server/sync-current-user.ts`
- Space create/join/validate/complete/invite API routes and their RPC result parsers
- `get-active-space-for-user.ts` and `has-active-space-for-user.ts`
- Settings server modules for reads, names, display names, and start dates

Required changes:

- Upsert users by `auth_subject` and let PostgreSQL generate internal IDs.
- Keep current public JSON contracts unless the new SQL contract proves a field unnecessary.
- Preserve generic unavailable responses and existing optimistic concurrency behavior.
- Remove assumptions in mocks that auth UUIDs are domain user UUIDs.

### 2. Unified memory preparation and finalization

Update:

- `apps/web-app/src/features/memories/server/create-memory.ts`
- `apps/web-app/src/features/memories/server/edit-memory.ts`
- `memory-input-validation.ts` and `edit-memory-input.ts`
- Create/edit upload and finalization API routes
- `apps/web-app/src/features/memories/utils/upload-staged-memory-photos.ts`
- Create/edit form hooks and `MemoryEditResult`

Required changes:

- Remove create/edit `Idempotency-Key`, request fingerprints, mismatch outcomes, and `reused` fields.
- Have preparation return `{ attemptId, uploads }`.
- Always prepare first, upload any originals, then finalize with `{ attemptId }`.
- Keep the attempt ID across recoverable finalization retries; reset it after form changes or terminal
  outcomes.
- Keep comment idempotency code untouched.
- Preserve current field validation, payload size limits, draft storage, and safe client errors.

### 3. Asset processing and cleanup

Replace or rename the persistence-facing responsibilities in:

- `process-staged-memory-photo.ts`
- `memory-photo-staging-cleanup.ts`
- `memory-edit-cleanup.ts`
- Their focused tests

Required changes:

- Query asset/object records instead of creation/edit staging tables.
- Record each object state transition through narrow RPCs.
- Validate original bytes before publishing any object as ready.
- Upload cover/detail variants to their pre-authorized object paths.
- Collapse both cleanup modules into one resource-cleanup boundary.
- Preserve bounded storage deletion batches and best-effort opportunistic invocation.

### 4. Memory reads and media delivery

Update:

- `get-available-memory.ts`
- `get-memory-photo.ts`
- `get-cover-preview-url.ts`
- `get-memory-detail.ts`
- `get-memory-for-editing.ts`
- Timeline, vault, and related-memory queries

Required changes:

- Rename persistence fields from cover photo to cover asset while preserving existing domain/UI fields
  where that avoids unrelated component churn.
- Read published assets ordered by `position`.
- Resolve only `ready` cover/detail objects; remove fallback to the original object.
- Verify memory and asset share the active space before downloading storage bytes.
- Preserve existing private URLs, pagination cursors, sorting, and `timeline | vault` behavior.

### 5. Comments, reactions, placement, and deletion

Application contracts should mostly remain stable. Update local result schemas or fixtures only where
the rebuilt RPC contract changes physical identity or asset field names.

Verify:

- Comments still preserve creation idempotency and versioned edit/delete behavior.
- Reactions still attribute display names through memberships.
- Placement still performs an atomic `updated_at` comparison.
- Memory deletion and unavailable-resource behavior remain non-enumerating.
- Removed assets are queued for cleanup instead of synchronously deleting external objects.

### 6. Remove obsolete contracts

Delete code and test expectations for:

- `memory_creation_attempts`, `memory_edit_attempts`
- `memory_photo_staging`, `memory_edit_photo_staging`, `memory_photo_cleanup`
- `memory_photos` and its three path columns
- Create/edit idempotency headers, fingerprints, reuse behavior, and duplicate-request outcomes
- Old lifecycle RPC names and migration filenames

Do not rename photo components, translations, routes, or user-facing copy merely because the database
uses asset terminology.

## Test Plan

### Migration contract

Replace migration tests tied to deleted historical filenames with one focused baseline contract test.
It should verify high-value invariants rather than every SQL line:

- Expected tables/enums exist in the baseline source and obsolete tables do not.
- Tenant-safe composite foreign keys and ownership XOR checks exist.
- Active membership and one-cover partial unique indexes exist.
- Every exposed table has RLS enabled.
- Security-definer functions use an empty search path and authenticated identity.
- Direct table grants are minimal and cleanup functions are service-role-only.
- Storage policies authorize exact asset object paths.
- Create/edit idempotency fields are absent while comment idempotency remains.

Delete superseded migration-source tests once equivalent assertions are represented in the baseline
contract test. Do not retain tests whose only purpose is proving historical migrations that no longer
exist.

### Application behavior

Update or add focused tests for:

- User synchronization by auth subject.
- Space create/join/rate-limit outcomes.
- Create and edit preparation with no assets, new assets, retained assets, ordering, and cover choice.
- Recoverable attempt continuation and terminal conflict/failure behavior.
- Invalid upload bytes and partial variant upload failures.
- Resource cleanup claim, success, missing-object success, failure, and retry behavior.
- Asset-based detail/edit/photo reads and rejection of non-ready or cross-space objects.
- Timeline/vault reads using the unchanged visibility values.
- Existing comment, reaction, placement, deletion, and settings contracts.

Tests should continue asserting observable results and narrow Supabase calls. Avoid reproducing the
entire SQL implementation in mocks.

### Database reset verification

Run from the repository root:

```bash
pnpm dlx supabase db reset
pnpm --filter web-app check
pnpm --filter web-app typecheck
pnpm --filter web-app test:run
pnpm --filter web-app build
```

After reset, inspect PostgreSQL/Supabase output for policy, function-signature, trigger, and storage
policy errors. A passing Vitest suite alone does not prove that the baseline migration executes.

## Manual Acceptance Scenarios

1. Sign in and sync a provider identity into one internal user.
2. Create a space, regenerate an invite, and complete onboarding.
3. Join as the partner and confirm both members see the same active space.
4. Create timeline and vault memories with zero, one, and five images.
5. Edit details, reorder assets, retain/remove images, replace the cover, and move visibility.
6. Retry finalization after a simulated recoverable failure without creating another attempt.
7. Confirm another space cannot read memory metadata or object bytes.
8. Create, edit, delete, and retry a comment; toggle each reaction.
9. Delete a memory and confirm its routes become uniformly unavailable.
10. Run cleanup and confirm abandoned/replaced storage objects are removed and rows marked cleaned.

## Rollback

Before merge, rollback is a normal branch revert. After a development deployment, restore the previous
migration directory and matching application revision, then reset the database. There is deliberately
no data rollback or compatibility path because this plan assumes disposable development data.
